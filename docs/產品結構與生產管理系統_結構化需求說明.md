## 1. 目的與範圍

### 1.1 這份文件要解決的問題

一家同時承接 OEM、ODM 與自有品牌業務的製造廠，其核心競爭力在於**接到詢價時，能快速且可信地回覆交期與價格**。

目前的作法依賴人的經驗與臨時詢價：每次新需求進來，生管與採購必須重新盤點庫存、重新詢問供應商、憑記憶推估交期。這使得報價速度受限於人力，且品質不穩定。

本系統的目標，是把**過去每一次實際發生的結構、價格、交期、良率沉澱為可查詢的資料**，讓下一次報價可以用查的，而不是重新問一輪。

### 1.2 系統的核心命題

> 一張訂單進來時，系統應能回答：**這批東西現在做，需要多久、大約多少成本、可以透過哪些路徑達成。**

要回答這個問題，系統必須同時掌握四件事：

1. 產品由什麼組成、要經過哪些工段（**產品結構**）
2. 每個工段有誰能做、多少錢、多久（**供應商與價格**）
3. 現在手上有什麼、在哪裡、還剩多少可用（**庫存與批次**）
4. 過去實際做起來如何（**實績資料**）

### 1.3 涵蓋範圍

本文件涵蓋：產品結構與衍生機制、工藝路線、物料分類、供應商與價格、模具治具管理、批次與庫存、外協管理、品管與追溯、訂單與報價估算、AI 介入規劃。

不涵蓋的部分見第 13 節。

## 2. 核心設計原則

> **這一節比任何功能清單都重要。** 以下六條原則若未被遵守，即使功能全部做出來，系統在現場也會無法使用。

### 2.1 系統提供事實與工具，判斷留給人

系統的職責是**如實記錄發生過什麼、目前狀態為何**，並在使用者需要時提供計算工具。系統**不應強制任何業務邏輯**。

典型案例——模具費：

- 系統記錄「這副模具投入 50 萬、已回收 50 萬、餘額為零」
- 使用者在報價時，即使餘額為零，仍要加收模具費 → **系統不得阻擋**
- 因為報價上的模具費可能是報價策略（壓低單價、拉高模具費），與實體模具的攤提餘額本就不必一致

同樣原則適用於：供應商選擇（系統列出候選與歷史數據，不自動選最佳）、交期估算（系統給出範圍，不保證）、成本計算（系統算出結果，允許人工覆蓋）。

**設計檢查點：** 每當出現「系統自動判斷 X」的需求時，先問——如果現場的人不同意這個判斷，他能不能覆蓋？如果不能，這個功能會逼使用者繞過系統。

### 2.2 不列舉情境，只定義不變的原子

製造現場的變化組合是無窮的：這批直送下一廠、那批回廠檢驗、MOQ 餘量寄在供應商、客戶的料放在加工廠等第二段排程⋯⋯

**試圖窮舉情境的設計必然失敗**，因為永遠會有第 N+1 種。

正確作法是找出不變的維度，讓情境由維度組合而成。以批次為例，只需要三個欄位：

| 情境 | 歸屬 | 位置 | 狀態 |
|---|---|---|---|
| 直送下一廠 | A廠 | 振動廠 | 加工中 |
| MOQ 餘量寄存 | A廠 | 毛胚廠 | 待發 |
| 加工廠自備料 | 供應商 | 供應商 | 不列入我方庫存 |
| 客戶料等第二段 | 客戶 | 加工廠 | 待排程 |

四種情境，同一組欄位描述完畢。未來出現第五、第六種，不需修改結構。

### 2.3 所有權與實體位置必須分離

這是 2.2 的具體展開，但重要到必須獨立成一條。

**東西是誰的（歸屬）** 與 **東西在哪裡（位置）** 是兩件獨立的事：

- 買斷的 MOQ 餘量寄在供應商 → 歸屬我方，位置在對方
- 委外加工中的在製品 → 歸屬我方，位置在對方
- 加工廠自己備的常用料 → 歸屬對方，位置在對方（我方僅知「該廠有現貨」）

若只用一個「庫存數量」欄位承載這兩件事，必然產生「實體上看不到但系統上還存在」的矛盾。

### 2.4 東西不會因為換型態或換位置而從帳上消失

A1-2 送去 CNC 變成 A1-3，帳上發生的**不是「消失一筆、新增一筆」，而是同一批物料的型態轉換**。

- 數量守恆（扣除不良與報廢）
- 價值只增不減（增加一段加工費）
- 任何時點都應答得出「這批料現在在哪、是什麼型態」

此原則是委外加工控管的核心，也是防止帳面黑洞的基礎。

### 2.5 資料的可信度本身就是資料

許多欄位（特別是在製品的預計完成日）是**人工維護、可能過期**的。系統必須記錄「這筆資料由誰、何時更新」，並在使用該資料進行估算時反映其新鮮度。

- 三天前確認過的交期 → 可用於承諾客戶
- 一個月未更新的交期 → 估算時應標示風險

**不應假裝所有資料都同等可靠。**

### 2.6 輸入形式的階梯：能不填就不填，要填就給選項

現場的資料品質，決定於輸入的摩擦有多大。**任何要求人自由書寫的欄位，最終都會空白、亂填、或被繞過。**

**設計時應依下列順序選擇輸入形式：**

| 優先序 | 形式 | 說明 |
|---|---|---|
| 1 | **不必輸入** | 由既有痕跡自動推算（見 11.6） |
| 2 | **是非題** | 「這批是否如期完成？」 |
| 3 | **選擇題** | 「延誤原因：□設備故障 □缺料 □品質重工 □其他」 |
| 4 | **填空** | 僅在前三者皆不可行時採用 |

> **僅僅是把填空改為選擇題，即可大幅降低人為失誤成本。** 選項是預先定義的，資料自然可統計、可比對；自由文字則無法。

**設計檢查點：** 每設計一個要人填寫的欄位，先問兩個問題——
1. 這個資料在別處有沒有留下痕跡，可以推算出來？
2. 如果非填不可，能不能變成選項？

## 3. 產品結構

### 3.1 三層概念必須分離

現場常把以下三件事畫在同一張圖上，但在系統中必須是**三組獨立資料**：

| 層 | 內容 | 為何要分離 |
|---|---|---|
| **BOM** | 產品由哪些部件組成、各用多少 | 換供應商不應導致 BOM 變更 |
| **工藝路線** | 每個部件經過哪些工段、順序為何 | 同一部件可能有多條可行路線 |
| **供應商與價格** | 每個工段有誰能做、價格與交期 | 供應商汰換頻繁，且一段多家 |

若三者揉為一體，供應商每次異動都需修改 BOM，資料量將失控。

### 3.2 BOM 基本結構

以範例產品 A 說明：

```
產品 A（完成品）
├── A1-4  部件 · 外協加工 · 用量 ?
├── A2    部件 · 直接採購 · 用量 ?
└── A3-2  部件 · 外協加工 · 用量 ?
```

**每一行必須包含：**

- 子項識別碼
- **用量（含單位）** — 「用 8」與「用 8 顆」是不同的資料，缺少單位必然出錯
- 損耗率／良率係數 — 交 1000 件成品，該段可能需投入 1080 件
- 有效期間（版本控制用）

### 3.3 工藝路線

部件若需加工，其路線由**有順序的工段**構成。工段數量不固定。

```
A1-1 → A1-2 → A1-3 → A1-4
毛胚    振動    CNC    陽極
```

**重要：製程類型是開放集合。** 毛胚、振動、CNC、陽極僅為此例。實際可能包含熱處理、壓鑄、噴砂、電鍍、雷雕、印刷等，取決於材料與設計要求。**系統不得將製程類型寫死為列舉值。**

**每個工段需記錄：**

- 順序
- 製程類型
- 產出物識別碼（每段產出為獨立物料，見 3.4）
- 候選供應商清單
- 標準工期
- 進料檢驗要求

### 3.4 每個工段的產出必須是獨立物料

理由是實務上的：**每段完成後，實體會離開該供應商、經過檢驗、可能入庫存放**。若無獨立識別，系統無法回答「現在有 300 件卡在振動廠」。

代價是物料筆數會快速膨脹，這是必須接受的成本。

> **關於識別碼：** 系統內部必須有穩定不變的識別碼（UID），此為批次區分、庫存結轉的基礎。但**該識別碼不需要人記憶、不需要有語意**。使用者介面應以「A1-2 振動完成品，B區3架」這類描述呈現，或直接支援自然語言查詢。料號是給人用的便利工具，不是系統的必要條件。

### 3.5 BOM 衍生機制 —— 本系統的關鍵功能

#### 3.5.1 問題的規模

硬體製造業的實態：**產品大類少，BOM 數量極多。**

> 實際案例：某供應商名義上僅有 18 項產品，但因應客戶對尺寸、規格、印刷的微調，衍生出的 BOM 達**上萬筆**。

差異可能小到只是「最後一段加一道雷射打標」或「LOGO 換一個」，但從 BOM 角度，那已是完全不同的產品。

#### 3.5.2 因此 BOM 不應儲存完整副本

若上萬筆 BOM 各自獨立儲存完整結構：

- 上游某工段換供應商或調價 → 需修改數千筆
- 想知道某副模具目前被哪些產品使用 → 查不出來
- 新版報價 → 必須重跑完整詢價流程

**正確作法：儲存差異，而非副本。**

```
BOM-0（第 0 代）：完整結構
 ├── BOM-A：繼承 BOM-0，差異 = 最後增加雷雕工段
 ├── BOM-B：繼承 BOM-0，差異 = 尺寸 20mm → 22mm
 └── BOM-C：繼承 BOM-A，差異 = 印刷內容變更
```

**帶來的效益：**

| 能力 | 說明 |
|---|---|
| 上游變更自動傳遞 | 母版工段改價，所有衍生版同步更新 |
| 反向查詢 | 可查出「此工段／此模具，目前有哪些產品在使用」 |
| 快速報價 | 新版成本 = 母版已知成本 + 差異部分，僅需詢價新增段 |

**代價：** 查詢時需展開繼承鏈，邏輯較複雜。相對於上萬筆各自為政，此代價合理。

#### 3.5.3 衍生關係需記錄

- 繼承自哪一版
- 差異內容為何
- 建立原因（哪個客戶、哪次需求）
- 是否共用模具（見第 6 節）

## 4. 物料分類

### 4.1 兩個獨立維度

現場習慣的四分類（完成品／部件／半成品／直購品）實際上混合了兩種不同性質的資訊。系統中應拆為兩個獨立欄位：

**維度一：層級屬性**（決定它在 BOM 樹的位置）

| 類別 | 定義 |
|---|---|
| 完成品 | 可對外銷售的最終產品 |
| 部件 | **加工已完成，下一步即為組裝** |
| 半成品 | **後續仍需加工** |

> 此處「部件」與「半成品」的區分是刻意的，且比業界常見的統稱「半成品」更精確。**部件可直接進入組裝排程，半成品不行。** 以範例產品：A1-1 至 A1-3 為半成品，A1-4 完成陽極後即為部件。

**維度二：取得方式**（決定它如何進來、如何記帳）

| 類別 | 定義 |
|---|---|
| 自製 | 廠內生產（本例中主要為最終組裝） |
| 外協加工 | **料為我方所有**，發給供應商加工，支付加工費 |
| 直接採購 | 供應商自備料，交付成品，支付貨款 |

### 4.2 組合範例

| 物料 | 層級屬性 | 取得方式 |
|---|---|---|
| 產品 A | 完成品 | 自製（組裝） |
| A1-4 | 部件 | 外協加工 |
| A1-2 | 半成品 | 外協加工 |
| A2 | 部件 | 直接採購 |

拆為兩軸後，不再出現「這東西既是部件又是直購品，該填哪一個」的問題。

### 4.3 直購品的特殊性

直購品（如螺絲、螺帽、華司）多為通用規格，**呆料風險低**——即使需求變更，仍可轉售或用於其他產品。此特性影響安全庫存策略與採購決策，建議在物料主檔標記「通用性」，供決策參考。

### 4.4 狀態轉換

同一批物料在路徑上前進時，其層級屬性會改變：

```
A1-3（半成品）→ 陽極加工 → A1-4（部件）
```

**這是狀態轉換，不是新增物料。** 呼應設計原則 2.4。

## 5. 供應商與價格

### 5.1 候選池與擇一發包

每個工段對應一組**候選供應商**，實際發包時擇一。

選擇依據包含：品質等級、價格、交期、報價有效期、材料與機具能力。

> **注意：候選供應商並非各段自由組合。** 前段的公差、表面狀態、材料證明會限制後段誰能接手；模具所在位置也會限制供應商選擇（見 6.4）。系統應能記錄此類**跨段相依限制**。

### 5.2 價格資料：照實儲存，不自行計算

與供應商洽談時，**階梯價區間、開機費等條件多已談定**。系統的職責是完整儲存該價目表並提供查詢，**不需自行推算量價關係**。

價目表應包含：

- 數量區間與對應單價
- 各項附加費用（見 5.3）
- 報價日期與有效期限
- 適用的材料、規格條件

### 5.3 費用的三種計次方式

不建議以「固定成本／變動成本」分類，因為檢驗費等項目會落在中間地帶。改以**計次基準**分類：

| 計次方式 | 說明 | 典型項目 |
|---|---|---|
| **按專案一次性** | 該物料首次生產時發生 | 模具費、治具費、首件檢驗、樣品費 |
| **按批次** | 每開一批發生一次，與數量無關 | 開機費、每批檢驗費、運費 |
| **按數量** | 隨件數計算 | 加工費（依階梯價） |

此分類的優點：**同一項費用不需爭論其歸類**，只需依實際計次方式登錄。首件檢驗填「一次性」，全批檢驗填「按批次」，抽樣數隨批量變動則填「按數量」。同一供應商可同時存在三種。

### 5.4 報價有效期

報價具時效性。系統應記錄每筆價格的取得時點與有效期限，並在使用過期資料進行成本估算時**明確標示**。

呼應設計原則 2.5：估算結果應附帶其資料基礎的新鮮度。

### 5.5 售價不在系統範圍

系統負責**誠實呈現成本**。最終報價的加成比例、客戶議價、專案性讓價，屬於業務決策，不進入本系統。

> 將成本計算與售價決策混合的系統，最終會導致兩邊都不準確。

## 6. 模具與治具

### 6.1 定位：獨立資產，非產品附屬

**模具是公司的生財工具，不是產品的附屬品。**

其性質類似公司購置的車輛：有取得成本、有使用年限、會折舊攤提，攤提完畢後仍可繼續使用，且後續維修仍為營運成本。

因此：

- 模具是**獨立的資產實體**，擁有自己的帳
- 產品與模具之間是「**使用**」關係，**多對多**
- 一副模具可被數十個衍生 BOM 共用
- 一個產品也可能使用多副模具

> **重要：登錄模具費不等於必須攤提。** 報價單上出現的模具費，可能是實際開模成本、可能是分次回收過去投入、也可能純粹是報價策略。系統不得強制其與實體模具的攤提餘額一致。

### 6.2 模具的帳

**支出面：**

- 開模費（原始投入）
- 歷次維修費
- 重做費

> **關於重做費：** 若要求原供應商重做模具，價格應顯著低於首次開模——設計圖面已存在，前期試錯過程無需重複。**此為談判籌碼，但前提是系統記得「原始開模廠是誰、圖面在誰手上」。** 故模具資料須包含圖面歸屬與原始供應商。

**回收面：**

- 各筆訂單已回收金額
- 目前未回收餘額

**使用面：**

- 目前有哪些 BOM 在使用
- 累計使用模數
- 壽命上限與剩餘可用模數
- 目前存放於哪家供應商
- 所有權歸屬（見 6.3）

### 6.3 攤提對象取決於業務型態

本廠同時承接 OEM、ODM 與自有品牌，三者的模具處理邏輯不同，故每副模具須標記其歸屬：

| 業務型態 | 模具處理 |
|---|---|
| **OEM / ODM** | 開模費通常攤提於客戶首批大量訂單的單價中。因無法確定是否回單，首次報價須將開模成本計入。客戶回單時，因模具費已攤提完畢，通常會據以降價。 |
| **自有品牌** | 模具為公司固定資產與營運成本，不歸屬特定客戶。 |

> **重要：即使是 OEM 案，模具所有權未必歸客戶。** 例如客戶僅要求更換 LOGO，模具實質上仍為我方所有。所有權歸屬須逐副記錄，不可由業務型態推定。

### 6.4 系統應主動提示的三件事

基於模具的使用面資料，系統可主動處理現場目前依賴記憶的工作：

**一、報價時提示攤提現況**
顯示該模具目前未回收餘額。**是否計入本次報價、計入多少，由使用者決定**（原則 2.1）。

**二、接單時預警壽命不足**
客戶下單 5,000 件，但模具僅剩 2,000 模 → 當場提示需確認修模或重開，並評估費用分攤。

> 此事若延至生產中途才發現，交期必然失控。

**三、變更供應商時提示模具位置**
模具現存於 B 廠，若欲改由 C 廠報價 → 提示需移轉或重開模具。此為 5.1 所述「跨段相依限制」的實體成因之一。

### 6.5 模數累計方式

上述功能均依賴「已使用模數」。現況推測為無人精確計算，僅在感覺接近極限時詢問供應商。

**建議作法：** 以累計生產數量推估。雖不精確（試模、報廢件亦消耗模數），但足以在接近上限時發出預警，供人工確認。

此為典型的「不完美但有用」的資料——**應標示為推估值，而非精確值**。

### 6.6 維修費分攤：不寫入規則

實務上，修模費用的分攤取決於金額大小與客戶關係：金額高則與客戶協商分攤，金額低則廠商自行吸收。

**此類依談判決定的事項，不應寫成系統規則。** 系統僅記錄「本次修模費用 X 元、由何方承擔」即可。

## 7. 批次、庫存與保留

### 7.1 批次的三個核心欄位

每一批物料同時記錄：

| 欄位 | 內容 |
|---|---|
| **歸屬** | 我方 / 供應商 / 客戶 |
| **位置** | 我方倉別 / 某供應商廠區 / 運送中 |
| **狀態** | 待檢 / 合格 / 不合格 / 加工中 / 已保留 等 |

三欄位組合可描述所有實務情境，無需列舉（見 2.2、2.3）。

### 7.2 路徑是逐批決定的

**「加工完成後回廠檢驗」或「直送下一加工廠」，並非工段的固定屬性，而是每批下工單時的決定。**

決定因素為該批的品質要求與檢驗需求。同一工段，本批直送、下批回廠，皆屬正常。

> **物流時間補充：** 本例供應商群聚於台灣，廠間運送時間通常在 3 小時內。因此**回廠與否主要為品質決策，對交期影響有限**。系統應以小時記錄物流時間，僅在跨區運送時納入交期主要計算。

### 7.3 MOQ 造成的分流

典型情境：供應商最低訂購量 5,000 件，本次僅需 1,000 件。

- 1,000 件直送下一加工廠
- 4,000 件**歸屬我方**（已買斷），**位置在供應商處**，未來隨需提取

此即「歸屬與位置分離」的實際應用。該 4,000 件是我方資產，須列入庫存與可用量計算，但實體不在我方倉庫。

### 7.4 庫存的三個數字

單一「庫存數量」欄位不足以支撐報價與排程。至少需同時呈現：

```
帳面量 － 已保留量 ＝ 可用量
```

**已保留量必須可展開至「被哪張訂單保留」**，不能僅有總數。因為急單協調時，生管需要判斷的是「這 300 件是誰保留的、該單急不急、可否挪用」——若系統僅顯示「已保留 300」，使用者仍須逐一詢問，系統即失去價值。

### 7.5 保留的時點

**保留應在生管盤點決定的當下即成立**，而非等實體備料完成。

現況作業存在約 24 小時的緩衝期：業務接單 → 生管盤點 → 人員備料出庫。此期間**實體已從庫存區移出，但帳面尚未扣除**。

若僅有單一數字，此落差即成為矛盾。以三欄位描述則無衝突：

| 面向 | 狀態 |
|---|---|
| 歸屬 | 已保留給 B 單 |
| 位置 | 已移至備料區 |
| 帳面 | 仍在庫存，尚未出庫 |

保留的本質是**承諾**，其作用在於防止同一批物料被重複承諾給不同訂單。承諾一旦作出即應生效。

### 7.6 在製品亦可被保留

保留對象**不限於現有庫存，亦包含在製與在途數量**。

範例：目前於 CNC 廠加工中的 500 件，若已由 A 單預定，則 B 單不得將其計入自身交期估算。

### 7.7 急單挪料

典型情境：

1. B 單急需 200 件，可用量不足
2. 系統顯示：A 單保留 300 件，交期尚有三個月
3. 生管決定自 A 單挪用 200 件
4. 解除 A 單保留，改保留予 B 單
5. **A 單因而缺料，須重新叫料**

**第 5 步為關鍵。** 挪料並非無成本的操作，它將風險轉嫁至被挪用的訂單。

> **系統要求：挪料與重新驗算必須成對執行。** 系統應在挪料操作的同時，立即重算被挪訂單的交期；若判定無法達成原承諾，須當場警示，使決策者在下決定的當下即知悉代價。

### 7.8 挪料的權限

**待決事項。** 見第 12 節。

## 8. 外協加工管理

### 8.1 數量閉環

料為我方所有、置於他方廠區，故數量必須閉環：

```
發出數量 ＝ 收回良品 ＋ 收回不良 ＋ 報廢 ＋ 仍在對方處
```

任何不平衡都須有人解釋。此為委外加工的核心控制點。

> **注意規則的正確表述：** 常見說法是「不允許加工廠代為備庫存」，但實務上存在例外——例如客戶的料因分兩段加工、暫置於加工廠等待第二段排程。
>
> 因此正確的規則不是「發出多少當場收回多少」，而是「**加工廠不得擅自動用歸屬他方之物料**」。前者是會被例外推翻的假規則，後者才是可執行的控制原則。

### 8.2 在製品的完成時間

**現況：** 供應商進度掌握依賴生管人員主動電話追蹤。供應商自主回報或上線填報的機制尚未成熟。

**因此，在製品預計完成日應如實定位為：人工維護、可能過期的估計值。**

**系統不應試圖自動化此流程，而應協助人維護它：**

| 功能 | 目的 |
|---|---|
| 記錄更新者與更新時間 | 判斷資料新鮮度 |
| 標示久未更新之項目 | 提示「此筆已三週未確認」 |
| 產出當日待追清單 | 將「今天該打哪幾通電話」系統化 |

此設計的關鍵在於：**它對生管人員是減負而非增負**，故有實際被使用的可能。

> **保留未來擴充空間：** 若日後導入供應商回報機制，此欄位結構不需變更，僅需在資料來源標記由「人工」改為「供應商填報」。現在不做，但不堵死。

### 8.3 在製品對交期估算的作用

在製品不是可用庫存（尚需完成後續工段），但**它會改變交期的答案**。

範例：

```
A1-4 現貨：0 件
A1-3 在 CNC 廠：500 件，預計 6 日後回廠
→ A1-4 最快可用時間 ＝ 6 日 ＋ 陽極工期 ＋ 檢驗時間
```

**若估算時遺漏在製品，系統會誤判為「須從第一段重新開始」，導致交期虛長十餘日、成本虛高。**

同時依原則 2.5，使用在製品估算交期時，須考量該完成日資料的新鮮度。

## 9. 品管與追溯

### 9.1 QC 是追溯的載體

**本系統的追溯機制，追的是檢驗紀錄，不是物料批次。**

理由：QC 是本來就要執行的作業，紀錄是自然產生的副產品。相較之下，全鏈批次追溯需要現場額外掃碼、額外分堆，缺乏執行動機，實務上資料品質往往低落。

每段進料的 QC 紀錄本身即帶有時間、物料、數量、來源、檢驗結果，這串紀錄構成可回溯的路徑。

### 9.2 追溯方式：推論式

**此為刻意的設計選擇，須明確認知其性質與限制。**

追溯流程：

```
出貨箱號 → 出貨時段 → 該時段運轉之機台 → 機台進料紀錄
→ 該時段進料來源 → 收斂至數家可能供應商 → （必要時）取回實品檢驗確認
```

**產出為「可能是這幾家」，而非「確定是這家」。**

**適用性判斷：**

| 情境 | 是否適用 |
|---|---|
| 客訴換貨、內部檢討 | 適用 |
| 找出應檢討的環節 | 適用 |
| 對外舉證、大額索賠 | 不適用 |

**為何不做全鏈批次追溯：**

- **大額賠償案**：數量大，自然涵蓋完整時段與批量，以現有紀錄即可鎖定供應商
- **零星不良**：補貨成本已含於成本結構中，追查源頭的成本高於損失本身

故全鏈批次追溯不列入需求。

### 9.3 追溯的斷點

物料進入我方倉庫後即混合，不再區分來源批次。此處為追溯鏈的斷點。

**實際可追溯深度取決於混料發生在哪幾個環節。** 若僅在最終組裝前領料，斷點單一，回溯仍可行；若每段皆入倉混合，則多段之後難以回溯。

此為現況限制，非系統缺陷。系統應如實反映可追溯範圍，不應宣稱超出實際能力的追溯精度。

### 9.4 檢討對象是流程，不是供應商

**供應商品質存在波動屬於常態；真正的問題是不良品為何通過檢驗、流入下一段。**

因此 QC 紀錄的價值不僅在於「合格／不合格」的結論，而在於**事後能否還原判斷過程**：

- 檢驗項目
- 抽樣數量
- 實測數值
- 判定人員
- **是否為特採（讓步接收）及其簽核人**

> **特採紀錄尤其重要。** 工程讓步接收的決定，往往是日後品質事故的源頭。此類紀錄必須留下完整痕跡。

### 9.5 檢驗方式

全檢或抽檢**視產業與產品性質而定，兩者皆存在**。系統須同時支援，並允許逐案設定。

抽樣標準是否隨供應商等級調整（新廠加嚴、穩定廠放寬）—— 尚未決定，見第 12 節。

### 9.6 物料狀態流

```
進料 → 待檢 →┬→ 合格 → 可進入下一工段或組裝
              ├→ 不合格 → 退回重做（返回上一工段供應商）
              └→ 不合格 → 報廢
```

**待檢狀態的物料不可動用。**

退回重做的成本歸屬（加工廠自身失誤／前段遺留問題），實務上多以協商處理。**若現場不實際登錄此資訊，則不應設計此欄位**——無人填寫的欄位比沒有欄位更糟。

## 10. 訂單與報價估算

### 10.1 這是整套系統的目的

前述所有結構，最終服務於此節。

**訂單進入時，倉庫未必有庫存。** 一般 OE 報價邏輯是：客戶詢價 → 回覆交期與價格。系統的價值在於使這個回覆能夠**快速、有依據、可信**。

### 10.2 步驟一：盤點庫存，判斷實際須生產的範圍

自產品 A 向下展開 BOM，逐層檢查現有可用量。**關鍵在於：每一層都可能截斷。**

| 現況 | 實際需執行 | 交期 |
|---|---|---|
| 完成品有現貨 | 直接出貨 | 物流時間 |
| 部件齊全 | 僅需排一次組裝 | 組裝時段 |
| A1-3 有庫存 | 僅需跑陽極一段 | 一段工期 + 組裝 |
| 全無庫存 | 從毛胚跑完四段 | 完整路徑 |

> **此判斷是交期估算中影響最大的變數，也是最能壓縮交期的環節。**
>
> 客戶下單量不大、且各部件皆有庫存時，理想情況僅需在產線安排一個時段完成組裝即可交貨。系統應能自動識別此類情況。

**盤點時必須使用「可用量」而非「帳面量」**（見 7.4）。否則報出的交期將系統性樂觀。

**在製品須納入計算**（見 8.3），否則交期將系統性虛長。

### 10.3 步驟二：對缺口部分，組出可行路徑

每個待生產工段有多家候選供應商，各自的價格、交期、品質水準不同。

**不應只輸出單一方案。** 建議至少提供：

| 方案 | 取向 |
|---|---|
| 最快 | 不計成本壓縮交期 |
| 最省 | 不趕時間、成本最低 |
| 平衡 | 常態選擇 |

理由：業務與客戶議價時，最常出現的問題是「能不能再快一點、快多少錢」。單一數字無法支撐此類對話。

**組合時須考量跨段相依限制**（見 5.1）——前段供應商影響後段可行選項，模具位置限制供應商選擇。**各段獨立選最低價的組合，可能根本不可行。**

> **呈現方式須遵循 11.4 之界線：三種方案並列，各自標明代價與歷史表現，不預設何者為佳。**

### 10.4 步驟三：輸出範圍值，而非單一數字

底層資料本身即具分布特性：同一家 CNC 廠過去十次交期落在 5 至 9 日，良率介於 96% 至 99%。

**強制收斂為單一數字，等同於偽裝確定性。**

建議輸出格式：

```
交期：18 – 24 日
成本：X – Y 元
信心水準：高／中／低
```

**信心水準的依據：**

- 該組合過去執行次數多 → 高
- 部分工段為新供應商、樣本少 → 標示該段為推估
- 使用之報價已過期 → 明確警示

呼應原則 2.5：估算結果應誠實反映其資料基礎的品質。

### 10.5 步驟四：實績回寫 —— 系統的命脈

**這是整套機制能否成立的關鍵，也是最容易在導入後流失的環節。**

每張訂單完成後，必須回寫：

- 實際交期（非計畫交期）
- 實際良率
- 實際發生成本
- 各批實測單耗（見 12.3）
- 延誤與否、延誤原因

**若僅在報價時查詢資料、完工後不回填實績，系統使用一年後的估算能力將與第一天相同。**

須留意：實績回寫在現場存在天然阻力（無人樂於登錄「本次延誤三日」）。此為管理課題，但技術上必須盡一切可能降低登錄成本——見原則 2.6 與第 11.6 節。

### 10.6 部分 BOM 與快速衍生報價

客戶詢價時，BOM **未必存在，但經常已有部分基礎**。

典型情境：客戶需求與現有產品相同，僅需在最後工段增加雷射打標或印刷。

**此時報價流程應為：**

```
沿用母版 BOM 之全部既有資料（價格、交期、良率）
＋ 僅針對新增工段詢價
＝ 數分鐘內產出報價
```

**這是 3.5 節衍生機制在報價場景的直接應用，也是本系統效率提升的主要來源。**

## 11. AI 介入

### 11.1 定位

本系統預期由 AI 參與操作流程。本節說明 AI 應介入之處、不應介入之處，以及導入順序。

**核心立場：AI 的角色與系統本身一致——提供事實與工具，判斷留給人**（見原則 2.1）。AI 不是這條原則的例外，反而是最需要嚴格遵守它的地方。

### 11.2 三個層次

AI 的價值分佈極不平均：**使用者最有感的功能，實質價值最低；價值最高的功能，使用者幾乎不會察覺。**

| 層次 | 內容 | 使用者感受 | 實質價值 | 對資料品質的要求 |
|---|---|---|---|---|
| 第一層 | 自然語言查詢 | 立即有感 | 介面改良 | 低 |
| 第二層 | 決策建議 | 有感 | **有重大爭議，須限縮** | 高 |
| 第三層 | 深層勾稽與參數提煉 | 幾乎無感 | **最高** | 中（且能反過來改善資料） |

---

### 11.3 第一層：自然語言查詢

#### 內容

使用者以自然語言查詢系統狀態，無需記憶料號或在多個畫面間切換。

```
「A1 那批現在到哪了」
「上個月做過的 22mm 那款，成本大概多少」
「哪些模具快到壽命了」
「這批料還有多少沒被保留」
```

此功能呼應第 3.4 節的立場：**料號是給人使用的便利工具**。若 AI 能直接回答「在 B 區 3 架、還有 320 件」，使用者是否記得料號即不再重要。系統內部仍需 UID，但可對使用者隱藏。

#### 性質認定

**這是介面改良，不是能力增加。** 背後查詢的仍是同一份資料，資料錯誤則回答必然錯誤。

#### 必要的防護

> **流暢的錯誤比生硬的錯誤更難被發現。**
>
> 系統回傳表格時，使用者會核對；AI 以完整句子回答「還有 320 件在 B 廠，預計週四回廠」時，使用者傾向直接採信。

**因此，AI 的每一則回答必須附帶：**

- 資料來源（哪張表、哪筆紀錄）
- **最後更新時間與更新者**
- 若資料已過期或久未更新，須主動聲明

範例：

```
A1-3 目前 320 件在 B 廠加工中，預計 3 月 14 日回廠。
⚠ 此完成日由王小姐於 2 月 20 日更新，已 22 天未確認。
```

**第二行比第一行重要。** 此為原則 2.5 在 AI 介面的具體落實。

---

### 11.4 第二層：決策建議 —— 須嚴格限縮

#### 爭議的所在

最容易被提出的需求是「讓 AI 自動選供應商組合、自動排程、自動報價」。

**此需求與原則 2.1 直接衝突，且衝突的方式不明顯，故須特別說明。**

#### 責任不對稱效應

即使將 AI 定位為「僅提供建議，使用者可自由推翻」，實務上會出現以下演變：

- 使用者推翻 AI 建議 → 後續出事 → **責任在使用者**
- 使用者採納 AI 建議 → 後續出事 → **責任歸於系統**

**此責任的不對稱，會使「建議」在數個月內演變為「事實上的決定」。** 使用者不是不能推翻，而是逐漸不敢推翻。

#### AI 看不見的決策依據

本產業的供應商選擇，大量依據不存在於系統中的資訊：

- 該廠近期經營狀況、人事變動
- 雖然報價較高但從未出過品質問題
- 此客戶關係特殊，交期絕對不能延
- 對方師傅即將退休，技術傳承有風險
- 過去的人情與長期合作關係

**AI 看不到這些，但它會給出一個看起來很有根據的建議，因為它算得出數字。** 數字的說服力與其完整性無關，這正是危險之處。

#### 因此的界線

> **AI 可以列出選項並說明各自的代價，但不排序、不標示推薦。**

此區別看似細微，實則關鍵：

| 允許 | 不允許 |
|---|---|
| 「這三個組合的交期與成本分別為⋯」 | 「建議選擇第二個組合」 |
| 「選 A 廠可省 3 天，成本增加 8%」 | 「最佳方案為 A 廠」 |
| 「此組合過去執行 12 次，平均延誤 1.5 天」 | 「此組合可靠度最高」 |

前者是提供事實，後者是代替使用者做判斷。

### 11.5 第三層：深層勾稽與參數提煉 —— 價值最高

此層使用者不會立即有感，但長期價值遠超前兩層。

#### 11.5.1 發現資料的不一致

系統中存在大量人工維護、可能過期的數值：在製品完成日、模具剩餘模數、供應商標準工期、標準良率。

**AI 適合執行的是持續的交叉比對，找出彼此矛盾之處：**

| 偵測項目 | 範例 |
|---|---|
| 標準值與實績脫節 | 某供應商標準工期記為 5 日，但過去 12 次實際皆超過 8 日 |
| 趨勢異常 | 某工段良率長期穩定，近三批下降 2 個百分點 |
| 帳實不符 | 模具帳載剩餘 8,000 模，依累計產量推算僅剩 2,000 模 |
| 資料停滯 | 某在製品完成日已 3 週未更新，且已超過原定日期 |

> **這些比對現在無人執行，因為需逐筆核對、人力不划算。但它們正是報價失準的根源。**

**此功能的附帶效益：它會反過來改善資料品質。** 相較於其他 AI 功能需要乾淨資料才能運作，此功能在髒資料環境中反而最有價值。

#### 11.5.2 從實績中提煉真實參數

第 10.5 節確立了實績回寫是系統的命脈。但**回寫進來的是原始紀錄，須經歸納才能成為可用參數**。

AI 應執行的歸納：

- 某供應商在特定材質、尺寸、公差條件下的**實際交期分布**
- 各工段的**實際良率分布**（非單一數值，而是範圍）
- 哪些條件組合**容易發生延誤**
- 各批實測單耗累積出的**真實損耗率**（見 12.3）

**提煉出的參數直接回饋至報價引擎，使其估算逐次精確。**

> **這是「系統越用越準」能否兌現的關鍵。** 缺少此層，實績回寫只會累積成一堆無人閱讀的紀錄。

#### 11.5.3 樣本不足時的相似性推估

第 10.6 節指出，全新產品詢價時缺乏歷史資料。

**AI 可執行相似性推估：** 依材質、尺寸、公差、製程類型，找出歷史上相近的工序，借用其數據進行估算。

**強制要求：**

- 明確標示「此為借用相似案例之推估值」
- 標示所借用的來源案例
- **信心水準必須標低**

此作法優於「無資料故無法估算」，亦優於「逕行給出數字而不說明依據」。

#### 11.5.4 QC 紀錄的異常偵測

第 9 節確立追溯採推論式，依賴事後翻查 QC 紀錄。

**AI 的價值在於不必等到出事才翻查**——持續掃描檢驗數據，偵測趨勢性漂移。

**其中最重要的是特採（讓步接收）監控：**

> 單次讓步接收不具意義，但若某供應商的特採率在半年內由 2% 升至 15%，此為極強的預警訊號，且在現況下幾乎不可能被察覺。

其他可偵測項目：

- 某檢驗項目的實測值持續朝規格邊緣漂移
- 特定判定人員的通過率顯著偏離同儕
- 某供應商的不良項目集中於特定類型

### 11.6 降低登錄成本 —— 守住系統命脈

**這是 AI 最不起眼、但最具關鍵性的用途，也是 AI 在本系統中最重要的目標。**

第 10.5 節指出，實績回寫存在天然的人性阻力。**若此環節失效，整套機制的自我改進能力即歸零。**

#### 11.6.1 兩條路徑，成熟度不同

| 路徑 | 作法 | 門檻 |
|---|---|---|
| **路徑一：讓人更容易輸入** | 手機掃碼、語音登錄、拍照辨識 | **高。** 需投入現場設備、改變作業習慣、取得現場人員配合 |
| **路徑二：不要求人輸入** | 從已存在的痕跡自動推算 | **低。** 不需改變現場行為 |

**應優先發展路徑二。**

送貨單、QC 紀錄、發票日期、入庫時間戳——這些痕跡本來就存在，只是散落於不同位置、格式不一。**AI 的價值在於把已有的痕跡串起來、反推出事實，而非要求人多做一個動作。**

範例：某批料的實際交期，不需生管填寫。系統可由進料 QC 紀錄日期或對帳單到貨日推算。**人只需在系統推錯時糾正——從「每筆都要填」變成「只在錯的時候說一聲」。**

#### 11.6.2 必須在設計庫存機制的同時就納入

**存在依賴關係：**

```
沒有庫存機制 → 沒有可信的進出紀錄 → 登錄再方便也無從驗證
```

手機登錄等工具屬於下一階段，因為若無結構承接、無法交叉驗證，方便的輸入只會讓錯誤資料更快進入系統。

**但這不代表可以延後思考。**

> **設計要求：庫存機制設計時，即須將「每個事件盡量由既有痕跡自動推算」列為設計條件，而非先做一套要人填的系統、日後再想辦法自動化。**
>
> 一旦現場習慣「那個欄位反正沒人填」，後續極難挽回。

#### 11.6.3 退而求其次：把填空變成選擇題

當某項資訊確實無法自動推算、必須由人提供時，依原則 2.6 的階梯處理：

| 形式 | 範例 |
|---|---|
| **是非題（優先）** | 「這批是否如期完成？」 |
| **選擇題** | 「延誤原因：□設備故障 □缺料 □品質重工 □其他」 |
| **自由填寫（最後手段）** | 僅在前兩者皆不適用時 |

**AI 的輔助角色：** 使用者若以自然語言回答「他們機台壞了」，AI 應自動歸入既有分類，使用者無需理解分類體系。

> **僅僅是把填空改為選擇題，即可大幅降低人為失誤成本。** 選項可統計、可比對、可用於後續參數提煉；自由文字則否。

---

### 11.7 AI 明確不做的事

以下限制，對實作方而言可能比「AI 能做什麼」更需要優先理解：

| 不做 | 理由 |
|---|---|
| 自動選定供應商 | 見 11.4，責任不對稱效應 |
| 為方案排序或標示推薦 | 同上 |
| 自動核准挪料、自動調整保留 | 涉及對客戶的承諾，須由人承擔 |
| 自動決定模具費是否計入報價 | 違反原則 2.1，該決定屬報價策略 |
| 自動判定特採是否放行 | 品質責任不可轉嫁予系統 |
| 自動修改標準值 | AI 可提示「標準值與實績脫節」，但修改須由人執行 |
| 強制填入單位換算係數 | 部分單位間無穩定關係，見 12.3 |
| **在無資料時生成看似合理的數字** | 見下方說明 |

> **最後一項尤其重要。** 本系統的價值建立在資料的可信度上。一旦 AI 開始生成無依據的數字，且該數字外觀與真實數據無異，整套系統的可信度將不可逆地崩壞。
>
> **無法回答時，必須明確說明無法回答。**

### 11.8 導入順序建議

**AI 對髒資料的容忍度低於人。**

現場人員知道「那個欄位大家都亂填的，不要看」「那家的交期要自己再加三天」。這些默契存在於人的經驗中，不在系統裡。AI 會依資料計算，然後產出**精確的錯誤答案**。

現況的資料基礎為：交期依電話追蹤、模數為推估值、實績回寫機制尚未建立、抽樣標準未定。**在此基礎上直接導入 AI 決策，風險過高。**

**建議順序：**

| 階段 | 導入內容 | 理由 |
|---|---|---|
| **第一階段** | 自然語言查詢（11.3）<br>**庫存機制設計時即納入自動推算（11.6）** | 對資料品質要求最低；提升使用意願；同時建立實績累積基礎 |
| **第二階段** | 資料不一致偵測（11.5.1）<br>QC 異常偵測（11.5.4） | 此階段反過來改善資料品質，為後續奠基 |
| **第三階段** | 參數提煉（11.5.2）<br>相似性推估（11.5.3） | 需累積足夠實績樣本後方能運作 |
| **後續階段** | 手機／掃碼／語音等現場登錄工具 | 需先有庫存機制可供驗證，否則無法確認其效益 |
| **持續限制** | 決策建議永遠止於「列出選項與代價」（11.4） | 非階段性限制，而是長期原則 |

## 12. 待決事項

> 以下項目**刻意暫不決定**，並非疏漏。多數是因為基礎結構尚未建立，此時討論將流於空想。文件中一併說明未決的後果，供實作方評估。

### 12.1 角色與權限

**現況：** 尚未拆分角色。

**理由：** 基礎結構未定之前，難以界定誰該有何種權限。

**未決的後果：** 誰可建立 BOM、修改供應商價格、執行報價、挪用他單保留料，目前無限制。**價格資料尤其需要保護**，長期無管控將導致資料可信度下降。建議在基礎功能穩定後儘早補上。

### 12.2 簽核流程

**現況：** 暫不處理。

**理由：** 在基本功能尚未建立時設計簽核，將阻礙推進。

**具體受影響項目：** 挪用他單保留料是否需業務同意（見 7.8）。實務上此操作會將延誤風險轉嫁至該業務的客戶，長期而言需要協調機制。目前作法為系統僅記錄異動與原因，不設簽核。

### 12.3 計量單位

**現況：** 每個品項各有其獨立單位，且**換算邏輯因品項而異，不存在通用規則**。

**已確立的規則：** BOM 每一行用量必須包含單位。

**單位換算須支援三種型態：**

| 型態 | 說明 | 範例 |
|---|---|---|
| **固定換算** | 存在穩定係數，可預先建表 | 1 箱 = 100 支 |
| **實測反推** | 無固定係數，須由實際投入與產出反算 | 投入 X 公斤原料，產出 N 件 → 單耗 = X ÷ N |
| **無法換算** | 兩單位間無穩定關係，各自獨立記錄 | 部分包材與成品之間 |

> **關於實測反推：** 此類單耗每批皆不同（受材質批次、加工餘量、損耗影響）。系統應逐批記錄，並累積為經驗值。
>
> **這些累積下來的實測值，本身就是真實的損耗率**，其可信度高於任何預設的標準值。此為第 10.5 節實績回寫的重要內容之一。

> **設計禁忌：不得強制要求所有單位組合都填入換算係數。** 對於無穩定關係者，使用者將被迫填入虛假數值，導致成本計算全面失真。**第三型態必須是合法選項。**

**未決部分：** 供應商報價單位與我方入庫單位不一致時的處理規則（如論支報價、論公斤入庫），須逐案確認採用上述何種型態。

### 12.4 與帳務系統的整合邊界

**現況：** 待討論。

**已形成的判斷：** 生管系統與帳務系統性質不同——前者管理實體流動（東西在哪、何時到達），後者管理價值流動（誰欠誰多少、何時認列）。兩者的更新頻率、精確度要求、使用者皆不同，不宜合併。

**故問題不在於是否整合，而在於介面設於何處。**

**建議先行釐清：** 以下動作同時具有生管與帳務意義，應列為介面清單：

- 進料入庫
- 領料出庫
- 外協發料與收回
- 報廢
- 完工入庫
- 出貨

建議模式：生管系統記錄實體事件，帳務系統訂閱事件產生分錄，兩系統各自獨立、事件單向流動。

### 12.5 抽樣標準

**現況：未決定。**

抽檢的抽樣標準是否隨供應商等級動態調整（新供應商加嚴、穩定供應商放寬）尚未確認。此影響 QC 資料表的設計細緻度。

### 12.6 起始資料與導入

**現況：暫無規劃，但預期會有一套導入方式。**

若確定推進，將以 Excel 表提供既有資料。

**須提醒：** 現有 BOM、供應商價目表、庫存數量、在製品狀態的整理與清洗，**工作量經常超過系統開發本身**，且為專案最常受阻之處。建議及早評估資料現況與缺口。

## 13. 明確不在範圍內的部分

以下項目**確認不在本次範圍**，列出以避免範圍蔓延：

| 項目 | 說明 |
|---|---|
| 售價與利潤加成 | 系統僅呈現成本，加成屬業務決策 |
| 原物料市價連動 | 庫存成本以實際交易價（歷史成本）認列，不做市價重估。鐵砂、鋼捲等原料端價格浮動需另建更新機制，本階段不處理 |
| 全鏈批次追溯 | 採推論式追溯，理由見 9.2 |
| 供應商自主回報平台 | 現階段機制尚未成熟，以人工追蹤為主，但保留未來擴充空間 |
| 現場行動登錄工具 | 手機、掃碼、語音等，須待庫存機制建立後方能驗證效益（見 11.6.2） |
| 應收應付、發票、出貨作業 | 屬帳務系統範圍 |

## 附錄：範例產品 A 的完整結構

```
產品 A（完成品 · 自製組裝）
│
├── A1-4（部件 · 外協加工 · 陽極）
│   └── 工藝路線：
│       A1-1（半成品 · 毛胚）  候選 SV × 1
│         ↓
│       A1-2（半成品 · 振動）  候選 SV × 3
│         ↓
│       A1-3（半成品 · CNC）   候選 SV × 3
│         ↓
│       A1-4（部件 · 陽極）    候選 SV × 2
│
├── A2（部件 · 直接採購）      候選 SV × 1
│   └── 通用規格品（螺絲、螺帽、華司等），呆料風險低
│
└── A3-2（部件 · 外協加工）
    └── 工藝路線：
        A3-1（半成品）         候選 SV × 1
          ↓
        A3-2（部件）           候選 SV × 1
```

**說明：**

- 各部件路徑**並行**，各路徑內工段**序列**
- 最終組裝由業主自行執行，不對外發包
- 工段數量不固定（A1 為四段，A3 為兩段，其他產品可能更多或更少）
- **製程類型為開放集合**，毛胚／振動／CNC／陽極僅為此例
- 每工段候選供應商擇一發包
- 全部部件備齊後，方可進入最終組裝

> **SV = Suppliers and Vendors（供應商）**。每家供應商各有其交期限制、價格、報價時段、材料與機具能力限制。
